# Read a verdict

When a pull request changes your LLM application, the gate posts one comment per pipeline and passes or fails the CI
job. This page takes the comment apart and says what to do for each outcome. Terms:
[Reference](/docs/reference#terms).

## The comment, piece by piece

A made-up booking assistant books, moves and cancels rooms through tools. A pull request rewrites the cancellation rule in
its system prompt and raises `delta` in `gate.yaml` from 5 to 10. The figure shows the gate's comment; its numbers
match this list.

1. **Pipeline and outcome.** Later runs edit this comment.
2. **Mean scores**, base → candidate, and the difference in points. "blocks below -5.00" marks −`delta`; a drop of
   exactly 5.00 passes. The line ends with the rule on the mean, here the naive rule, the default. Under
   `mean: betting` the line has no "blocks below", and the next one gives a range
   ([Lines of the betting rule](#lines-of-the-betting-rule)).
3. **What was compared.** The naive rule reads the first run of each case, even when `k` asks for more; the betting
   rule reads them all. The line on checks after it reads all runs and names the checks that broke, or how many runs one would need to show. Each `config` hash covers the whole
   version; `set` is the test set's hash. When the base's runs came from earlier jobs, a line follows, for example
   "Base: 20 of 20 runs come from earlier jobs; the oldest ran 5 hours before the candidate's"
   ([where from](/docs/how-it-decides#where-the-bases-runs-come-from)).
4. **Model without a date.** Not in this example: a warning that both versions' runs had no pause longer than an hour
   and, where both asked for the same model, got the same one, or the gate would have refused to compare them.
5. **Cost of the decision.** Every call that got an answer, both sides, at the target branch's list prices; base runs
   reused from earlier jobs are left out.
6. **Budget.** See [The budget line](#the-budget-line).
7. **Cases that got worse.** Up to five, largest drop first, on any outcome. The [dashboard](#the-dashboard) lists
   every case.
8. **Notes.** Here the gate still blocked at 5: the rules come from the target branch
   ([Notes under the comment](#notes-under-the-comment)).
9. **Job log.** The CI run and both versions' logs.

## The budget line

The budget line checks the candidate alone. "not shown over its limits" is weaker than "within its limits": no limit
was clearly exceeded. "over: …" names the broken limit and turns a pass into `budget fail`; "(not checked:
…)" names a limit the runs could not decide. A `?` in the latency interval marks an end the runs cannot give. A quality
fail stays a quality fail whatever the budget says
([How it decides](/docs/how-it-decides#budgets-cost-and-latency)).

## Lines of the betting rule

Under `mean: betting` the mean line names the rule, and the next line says what the runs showed:

| Line | Meaning |
|---|---|
| After run N of each version the difference lay in [LOW, HIGH] points (95 %), which decided. | The rule decided at run N, the first look that showed a side; the range is that look's. Later runs do not change the decision, so the mean line, which covers every run, can lie outside this range. |
| ⚠️ Shown worse than the base, but by less than δ. | A pass, but the whole range lies below 0: a real loss smaller than `delta`. Such losses can add up over requests. |
| The difference lies in [LOW, HIGH] points (95 %); not decided. A pass needs at least N runs of each version even if nothing changed (…): M more, about $X outside CI (a new CI job runs all N afresh). | `inconclusive`. N is what a candidate that scores like the base in every run would need, so a noisy one needs more. The cost appears with `prices`. Past 10 000 runs the line says so instead: add cases. |
| …; not decided. A pass needs at least N runs … ; these K did not show it: the versions differ, or the noise needs more. | `inconclusive` with more runs than a candidate identical to the base would need: the runs differ, by a real loss or by noise. |

The line with the configs then says "N runs of each version" instead of "first run of each version".

## Lines of levels

With `levels` in `gate.yaml` ([Critical and minor checks](/docs/how-it-decides#critical-and-minor-checks)), the line
"Checks: …" covers only the checks that may block, and the comment can add:

| Line | Meaning |
|---|---|
| "· ⚠️ 1 minor check worse" (or "reported check") at the end of the title | A minor check passed significantly less often. It does not block; `warnings` in `verdict.json` lists it, and GitHub Actions shows a warning on the job. |
| ❌ Critical checks broke: `no-fee-waiver` in cancel-after-deadline. | Right under the title: a critical check passed significantly less often, which blocks even under `checks: report`. It names up to five. |
| Checks that only report (minor; normal under `checks: report`): … | The rule on checks for the checks that cannot block, tested apart from the others. Their broken checks get a table of their own at the end. |
| Minor cases, out of the mean: … | Cases with only minor checks; the mean leaves them out. |
| ⚠️ Levels that match no check of this set: critical: credit-*. | A pattern that matches nothing, often a typo; the checks it was meant for stay normal. |

## Notes under the comment

| Note | What to do |
|---|---|
| gate.yaml in this request changes … so every pipeline runs. | Expect every pipeline to run and cost money. |
| ⚠️ The target branch's gate.yaml is not valid … | Fix it: until then a request can loosen its own gate. |
| `booking` is new in gate.yaml … | See [No base version](#no-base-version). |
| ⚙️ This request changes the gate's rules … | Nothing, unless the request should be judged by the new rules: then merge them first, in their own request. |
| This request changes the test set … | Review case edits as code: a request that deletes or loosens its failing cases passes without being better. |
| ❌ This request removes `faq` … | See [Inconclusive](#inconclusive). |
| Base ran again: this job cannot read earlier runs … | Add `actions: read` to the job's `permissions`. |

## What to do for each outcome

| Outcome | Exit code |
|---|---|
| ✅ pass, ⏭ unchanged, 🆕 no base version | 0 |
| ❌ quality fail | 10 |
| ⚠️ inconclusive, or a ❌ note under another title | 11 |
| ❌ budget fail | 12 |
| ⚠️ infra error | 20 |
| not checked: no comment | the step exits 1 |

Any code other than 0 fails the job, which blocks the merge only once it is a required check
([Exit codes](/docs/reference#exit-codes)).

### Pass

The rule on the mean passed: under the naive rule, the mean of the candidate's first runs was no more than `delta`
points below the base's; under the betting rule, the runs showed a loss smaller than `delta`. No check that may block
got significantly worse over the runs, and the candidate was not shown over a budget. Read the cases that got worse and
any ⚠️ line anyway: a mean can hold while single cases drop
([What a pass means](/docs/how-it-decides#what-a-pass-means)).

### Quality fail

The rule on the mean blocked, or a check that may block got significantly worse over the runs (a table names it; a
critical one also opens the comment). Open the cases in the table in the
[dashboard](#the-dashboard) or [artifact](#the-artifacts) and look for a check that flips: in the example,
`cancel-after-deadline` fails `no-fee-waiver` because the agent called `waive_fee`. Under the naive rule with `k: 1`,
one run of each version decides the mean, and scores move with no change: in the author's measurement, one unchanged version of a support agent scored
between 0.40 and 0.70 over 11 runs on the same 10 tasks, 30 points, six times the default `delta`. A block is more
likely real when the failing checks match your change. Fix it and push, or merge a new `delta` first in its own
request; re-running until it passes defeats the gate.

### Budget fail

Quality passed, but the candidate broke a cost or latency limit; "over:" names it. Compare both sides in the cost line,
and each run's tokens, latency and steps in the dashboard. Make the change cheaper or faster, or raise the budget first
in a request of its own.

### Inconclusive

Two things give `inconclusive` (exit 11):

- **The betting rule could not decide.** The title reads "⚠️ inconclusive", and the
  [line under the mean](#lines-of-the-betting-rule) says how many runs of each version a pass needs and roughly what
  the missing runs cost. Raise `k` in the target branch's `gate.yaml` in a request of its own, and later requests get
  the runs. Rerunning this request's job is a second test of it: two tries can pass a loss of `delta` wrongly in up to
  about 5 % instead of 2.5 %. Or a maintainer reads the range and merges over the check.
  A check that blocks makes it a quality fail instead.
- **A request removes or renames a pipeline in `gate.yaml`.** The other pipelines keep their titles, add the ❌ note
  and exit 11 unless something worse happened. If the removal is meant, a maintainer merges over the check; a renamed
  pipeline gets `no base version` under its new name.

### Infra error

The gate could not reach a verdict; it says nothing about quality. The comment gives the reason and the
end of the failing step's log. If only the candidate did not finish its runs, your change is the likely cause; for
rate limits or an outage, re-run the job; for quota or a wrong key, fix the repository's secret.

### Unchanged

The request leaves this pipeline's version as it is, so nothing ran and the job passes. If you expected a run, your
change touched only files that do not count, such as documentation, `.github/`, `gate.yaml`, ignored paths or test
sets ([What a version is](/docs/how-it-works#what-a-version-is)). Edited cases run on the next request that changes
the version.

### No base version

The target branch has no version of this pipeline, as when a request adds the gate or a new pipeline. The candidate
ran alone and nothing blocks. Check its score: after merge, this version is the base.

### Not checked

The request comes from a fork, so GitHub passes no secrets: the gate runs nothing, posts no comment, and the job fails.
To gate it, a maintainer reads the change and pushes the branch to this repository.

## No comment on the request

- A fork: see [Not checked](#not-checked).
- The job cannot comment: give it `permissions: {contents: read, pull-requests: write}`.
- A step before the gate failed.
- A pipeline's step was skipped: every step but the first needs `if: ${{ !cancelled() }}`.
- The workflow does not run on `pull_request`.

## The artifacts

Each gate step keeps `release-gate-NAME-ATTEMPT`, with the comment, `verdict.json`, both versions' records and the
logs, for the repository's artifact retention period, and `release-gate-NAME-ATTEMPT-cases`, with the test set's text
files, for 30 days. A record is one JSON line per run ([fields](/docs/reference#the-record-of-a-run)). To read one case on both
sides (`RUN_ID` ends the "Job log" link):

```sh
gh run download RUN_ID --name release-gate-booking-1 --dir gate-out
jq -c 'select(.case == "cancel-after-deadline") | {rep, score, hits, error}' gate-out/base.jsonl gate-out/candidate.jsonl
```

## The dashboard

The [dashboard](/docs/dashboard) reads the gate's artifacts after each run, once its GitHub App is installed on the
repository; the records then leave CI for its database. It shows every case of a run, with both sides' answers,
checks and trace steps.
