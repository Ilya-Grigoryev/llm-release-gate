# Method

The gate is the tool of a Bachelor thesis. Anything marked planned on this page is not in the gate yet.

## The problem

An LLM application can give different outputs for the same input, so a drop of a few points between two versions can
be a regression or noise. A gate that cannot tell them apart blocks harmless changes or is loosened until it catches
nothing.

In the [author's measurement](/docs/how-it-decides#the-same-version-answers-differently), a support agent with its
config, prompts and code unchanged ran its 10 cases 11 times; its mean score ranged from 0.4 to 0.7, 30 points, six
times the gate's default threshold of 5 points. A one-call extraction application on 30 documents moved its mean by
less than 2 points over 10 repetitions. Noise depends on the application, so a gate has to measure it rather than
assume it.

## Research questions

These are drafts.

1. **Design.** How should a release gate for LLM applications be designed so that one tool fits any application, from
   a single model call to a tool-using agent, and a team can adapt it with little effort?
2. **Decision rule.** Under run-to-run noise, how do the naive rule, a statistical rule, the same rule with adaptive
   extra runs, and the rules of existing tools compare in false blocks, missed regressions and cost per decision?
3. **Noise.** How does run-to-run noise change from a single call to a multi-step agent and a chat with a simulated
   user, and does that change which rule a team should use?

## Contribution

**1. The tool.** A release gate that a team sets up with a few files: how to run the application, its cases with
checks, and one `gate.yaml` with the rules. Built today: the runner, traces, 16 kinds of checks, one JSON protocol for
any program, the naive rule and a betting rule on the mean, the rule on checks with critical and minor checks, budgets,
and a GitHub Action that comments the verdict. Planned: adaptive extra runs and an anchor comparison.

**2. Evidence for the decision rules (planned, stage D):** how often each rule blocks a harmless change, misses a
regression or leaves the decision open, and what one decision costs, on recorded runs of real applications, not on
synthetic noise. Until then, this site states no error rates.

By their documentation, small open-source gates such as statgate and flipcheck check false alarms on synthetic or
simulated data ([Limits and comparison](/docs/limits#how-it-differs-from-other-tools)).

## Decisions: fitting any application

Every LLM application is a sequence of model calls and actions, from a single call to an agent with tools or a chat
with a simulated user. The gate records each run as a trace of steps, so one gate and one set of checks cover the
range.

The decisions below answer the first research question; D-numbers are the thesis's decision records.

- **A version is what git sees** (D-025, built): its config, the bytes of its prompts and the repository's code as git
  sees it, not a version number raised by hand.
- **The rules come from the target branch** (D-024, built), so a pull request cannot raise its own `delta`.
- **Any program, one protocol** (D-023, partly built): an engine with one JSON protocol, not a Python dependency or an
  SDK with a hosted service. Today the gate is still added to a project as a dependency.
- **Checks that the team writes** (D-019, D-020, D-022, partly built), over the answer and the trace.
- **No model grades the text by default** (D-005, D-022); a model-graded check is planned as an option.
- **Models without a date** (D-018, D-029, built) are accepted: one name is one model, with
  [precautions](/docs/how-it-decides#where-the-bases-runs-come-from).

## Decisions: deciding under noise

These answer the second research question. By default the gate uses the naive rule with a fixed `delta` (δ), 5 points
by default, and the rule on checks; `mean: betting` turns on the statistical rule. The anchor and running more on its
own are planned; the rest is built.

- **Both versions run on the same cases, in the same job** (D-007, D-018, D-033, built), so a case's difficulty and a
  shift in the service between sessions cancel out. With `base_max_age_hours` above 0 the base's runs come from earlier
  jobs within that many hours, so a shift in the service within that window counts as an effect and the requests in it
  share one base sample
  ([Where the base's runs come from](/docs/how-it-decides#where-the-bases-runs-come-from)).
- **A pass speaks for these cases** (D-004, built), as a test suite does, not for inputs like these.
- **δ is the loss you accept** (D-004, built), specified in advance and not tuned to the noise.
- **Three outcomes** (D-004, D-026, built): pass, block, or "not sure yet" (`inconclusive`) with the runs and the money
  a pass needs, as the figure below shows.
- **A money limit instead of `k`** (D-026, D-032, built): with `max_spend_usd` the gate buys rounds until it decides
  or the next round would not fit; it reads the checks once, on rounds 1 to 5 (1 to 2 when no check can block), and
  a re-run of the job continues with the same pairs of runs ([Adaptive runs](/docs/how-it-decides#adaptive-runs-a-money-limit-instead-of-k)).

The betting rule says \"not sure yet\"; more runs narrow the interval."} alt={"Four example intervals against the margin \u2212\u03b4. - **Intervals that stay valid when runs are added** (D-011, built): betting confidence sequences (Waudby-Smith and
  Ramdas, arXiv:2010.09686), with run k of a case paired with run k of the base. An experiment compares variants of
  the bet.
- **An anchor against slow creep** (D-012): each pull request is also compared with a fixed earlier version, so losses
  smaller than δ cannot add up unseen.
- **Checks that break on their own** (D-003, built): a check that passes significantly less often over the runs
  blocks; at the default `alpha` a single broken check can block from 4 runs of each version. Critical checks block even when the others
  only report, minor ones only warn (D-028, built).

## Planned experiments

Planned for stage D; no results yet.

- **Where the truth comes from.** The same version against itself (A/A), where any block is a false block; mutants,
  small deliberate breaks caught only if the gate blocks them; and real, harmless edits, whose right answer is not
  decided yet.
- **Rules compared.** The naive rule, the betting rule with and without adaptive extra runs, and the rules of
  existing tools.
- **Data.** Recorded runs (K runs of each of N cases) from a single call to an agent in a chat, resampled by a
  simulator without model calls. A held-out pool from a different calendar week confirms the main results.
- **Measures.** Harmless changes blocked, regressions missed, decisions left "not sure yet" at the run limit, and the
  cost and time of one decision.
- **Pre-registration.** Every experiment is written down before its data exist.
