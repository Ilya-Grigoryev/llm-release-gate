# Reference

The exact names of what you write for the gate and what it writes back, for release `v0.1.0-dev.12`. Tables labelled
"from … .schema.json" are built from the JSON Schemas the gate validates against. Today the gate decides with the naive
rule ([How it decides](/docs/how-it-decides)); the
[planned statistical rule](/docs/how-it-decides#planned-several-runs-and-an-interval) uses every run, can answer "not
sure yet" (exit 11) and adds its interval and seed to the verdict.

## Terms

- **Pipeline**: one LLM part of your application, gated on its own, with its own version, test set, verdict and
  comment.
- **Version**: a pipeline's config, the bytes of its prompts and the repository's code as git sees it
  ([What a version is](/docs/how-it-works#what-a-version-is)).
- **Base and candidate**: the version on the target branch (the branch the pull request merges into) and the version
  in the request.
- **Case, check, run**: a case is one test, its inputs and expected values; its checks score an answer from 0 to 1; a
  run is one version handling one case once, `k` times per case.
- **Runner, program, the action**: the runner (`llm-release-gate run`) makes one version's runs; for each it starts
  the program the version's config names ([Connect your app](/docs/connect)). The action is the GitHub Action that runs
  `pr` and `comment` for one pipeline.

## gate.yaml

It lives in the project's directory: the repository's root, or the one you pass as `--project` (`project-dir` in the
action). Top-level
settings apply to every pipeline; a pipeline's own setting replaces them. The rules (`k`, `delta`, `prices`,
`budgets`, `base_max_age_days`) come from the target branch, so a request that edits them runs under the old ones, unless
the target branch has none or a broken one ([Whose rules apply](/docs/how-it-works#whose-rules-apply)).

```yaml
pipelines:
  invoice:                                # names the comment and the artifact
    config: configs/invoice.yaml          # the version
    golden: golden/invoices               # its test set
    manifest: manifests/invoices.yaml     # ids and hash the set must match
    inputs-url: https://files.example.com/invoices/{path}
  booking:
    config: configs/booking.yaml
    golden: golden/booking
    k: 3                                  # this pipeline's own setting wins
    budgets: {cost_per_run_usd: 0.02, latency_s: 30}  # replaces the top-level budgets as a whole
k: 1
delta: 5
prices: prices.yaml
budgets:
  cost_per_run_usd: 0.002
  latency_s: 8
  latency_quantile: 0.95
prepare: [npm, ci]
ignore: [web/, "**/*.ipynb", "!docs/kb/"]
```

What the schema does not say:

- **Names**: letters, digits, `_`, `-` and `.`, not starting with `.`; the name also labels `OUT/NAME`.
- **`golden`**: both versions run on the request's test set.
- **`base_max_age_days`**: comes from the target branch, like `delta`. The gate never reuses runs when either version's model has no date, when the request changes `prepare`,
  or when the target branch has no valid `gate.yaml`.
  ([Why](/docs/how-it-decides#where-the-bases-runs-come-from))
- **`delta`**: points out of 100; a drop of exactly `delta` passes. Only `gate --relative` makes it relative.
- **`prices`**: commit the price file; the gate copies the target branch's before `prepare` runs. `pr` passes it to the
  comparison only, so the records have `prices_hash: null`.
- **`prepare`** is followed by `uv sync --locked` in each tree.
- **`ignore`**: globs from the project's directory. `*` stays within a directory, `**` crosses directories, a trailing
  `/` takes a whole directory, a pattern without `/` matches a file name at any depth, `!pattern` takes files back.
- **Changes that run every pipeline**: changing `ignore`, adding, removing or renaming a pipeline, changing a
  pipeline's files (config, prompts, test set, manifest, price file) or the top-level `prices` path, and any request
  while the target branch has no valid `gate.yaml`.
- **`inputs-url`**: `{path}` is the input's path as the case names it, `{name}` its file name. Only `https` links are
  shown.

## A version's config

A YAML file per version, checked when the gate loads it. `run` reads the nearest `gate.yaml` above it.

```yaml
# configs/booking.yaml: the booking assistant (example)
command: [node, agent.js]
model: gpt-5.4-mini-2026-03-17
prompt: {system: ../prompts/system.md, summary: ../prompts/summary.md}
input: ticket
params: {temperature: 0}
timeout_s: 120
```

| Key | Required | Meaning |
|---|---|---|
| `command` | yes | the program that answers a case and its arguments, as a list, from the runner's working directory |
| `model` | yes | prefer a dated snapshot ([why](/docs/how-it-decides#where-the-bases-runs-come-from)) |
| `prompt` | yes | a file, or name → file, relative to the config |
| `input` | yes | the case input this version reads |
| `params` | no | API parameters, passed on; a whole float becomes an integer |
| `max_retries` | no, default 5 | retries after exit 75 or a timeout; backoff 1, 2, 4… s, at most 60 s |
| `timeout_s` | no, default 60 | seconds before the program is killed and the run retried |

The version's hash covers every key (key order, formatting and `0` versus `0.0` do not change that part), the prompts'
bytes and the code git tracks. The config file is tracked by git, so it counts as code too: reordering its keys still
gives a new version. [What a version is](/docs/how-it-works#what-a-version-is) lists what does not count.

## Price file

```yaml
# prices.yaml: USD per 1M tokens, [input, output] or [input, output, cached input].
# Example numbers: copy your provider's current list prices.
gpt-4.1-mini: [0.40, 1.60, 0.10]
gpt-5.4-mini: [0.75, 4.50, 0.075]
```

Keys are prefixes of model names; the longest match wins. Without the third price, cached input costs the full input
price. A model without a price has an unknown cost, and a cost budget then gives `infra error`.

## Manifest

For a test set built or fetched outside git: `pr` and `golden validate --manifest` fail unless the set has exactly these
ids and this hash.

```yaml
# manifests/invoices.yaml: the case ids, and the hash `golden validate` prints for your set (example value)
ids: [inv-001]
sha256: 06a116fb83a555e7d4ee07df3de681cf15fc48f46a8d398f0c71ef21ae629f40
```

Copy the hash from `golden validate` on your own set. Keep the manifest outside the test set.

## Cases

A test set is a directory; each `.yaml` or `.yml` file directly in it is one case. Inputs are files anywhere inside
the set, with paths relative to the case; a YAML input goes in a subdirectory. The set's hash covers each case's parsed
content and each input's bytes. [Write tests](/docs/write-tests) explains cases and checks.

```yaml
# golden/booking/late-cancel.yaml: the booking assistant (example)
id: late-cancel
version: 1                      # the case's own revision, not the pipeline's version
input:
  ticket: late-cancel.txt       # an input next to the case file
expected:
  state_change: {bookings: {B-1042: cancelled}}
scoring:
  method: checks
  aggregate: all
  checks:
    - {id: state, kind: state, key: state_change}
    - {id: looked-up, kind: order, first: find_booking, then: [cancel_booking]}
    - {id: right-booking, kind: called, tool: cancel_booking, args: {booking_id: B-1042}}
    - {id: no-fee-waiver, kind: not_called, tool: waive_fee}
    - {id: steps, kind: max_steps, max: 12}
    - {id: reply, kind: regex, field: reply, pattern: "B-\\d+"}
```

### Fields of a case

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | unique in the set; letters, digits, `.`, `_`, `-` |
| `version` | yes | the case's own revision, a whole number ≥ 1 |
| `input` | yes | input name → file path |
| `expected` | yes | the values the checks compare against; a program never receives them |
| `scoring` | yes | how the answer is scored, below |
| `slices` | no | labels, name → text |
| `source` | no | text |
| `note` | no | text |

The gate does not read `version`, `slices`, `source` or `note` today; they still count in the set's hash.

| `scoring` key | With method | Meaning |
|---|---|---|
| `method` | — | `field_match` or `checks` |
| `aggregate` | both | `mean` (default) or `all` (1 only if every scored result is full) |
| `normalise` | `field_match` | for every string field: `whitespace`, `casefold` |
| `fields` | `field_match` | field → `{type, normalise}`; `type` is `string` (default), `number` or `date`, compared by value |
| `checks` | `checks` | the list of checks, next section |

With `field_match`, a field expected as `null` is not scored; the case score is the share of right fields.

## Checks

A check gives true, false, a share from 0 to 1, or nothing when it does not apply; one over many items gives a result
each (`id.FIELD`, `id.N:tool`). Ids are unique, and none may start with another id plus a dot.

| `kind` | Keys besides `id` and `kind` | Passes when |
|---|---|---|
| `field_match` | `expected` (default `fields`), `field`, `normalise`, `fields` | one result per expected field, as in `scoring.method: field_match` |
| `exact` | `value` or `expected`, `field` | the text equals the value, ignoring surrounding spaces |
| `contains` | `value` or `expected`, `field` | the text contains the value, ignoring case |
| `regex` | `pattern`, `field` | the pattern matches somewhere in the text |
| `number` | `value` or `expected`, `field`, `tol` | within `tol` (default 0) of the value; `$1,249.50` counts as a number |
| `json_schema` | `schema`, `field` | valid against the JSON Schema (draft 2020-12) |
| `refusal` | `value` or `expected`, `field` (default `answer`) | refusal expected: the field is present and `null`; not expected: it is filled. A missing answer is not a refusal |
| `called` | `tool`, `args`, `actor` | the tool was called with matching arguments and the call went through |
| `not_called` | `tool`, `args`, `actor` | never tried with such arguments; a refused call counts as tried |
| `order` | `first`, `then`, `actor` | every call of a `then` tool comes after a call of `first`; true if no `then` tool was called |
| `max_steps` | `max`, `actor` | at most `max` answered model calls, not counting those with a `purpose`; true with none |
| `active` | `actor` | at least one tool call went through |
| `actions` | `actions` or `expected`, `actor` | one result per expected `{tool, args}`: called with matching arguments |
| `state` | `key` (`final_state`, default, or `state_change`), `expected` | the trace's value under `key` equals the expected one (default: the case's expected value of that name) |
| `doc_found` | `ids` or `expected`, `actor` | the share of expected document ids the actor retrieved; not scored without expected ids |
| `function` | `function` (`module:function`), any keys of your own | your function returns true, false, a share or nothing ([how](/docs/what-it-catches)) |

- `value`: the check's own value; `expected`: a dotted path into the case's `expected`; `field`: a dotted path into the
  answer (default: all of it); `actor`: `agent` (default), `user`, `system` or `env`.
- `args`: a plain value must match exactly; a mapping holds operators `eq`, `ne`, `gt`, `gte`, `lt`, `lte` (these four
  take a number) and `in` (a list). `{eq: {...}}` matches a mapping value.
- Trace checks read the runner's last attempt and fail without a trace; `called`, `active`, `actions` and `order` also
  count `unknown` calls.
- `golden validate` checks every check without running it and rejects keys a kind does not know (except in `function`).

## Protocol

For each run the gate starts the program in the runner's working directory, writes one JSON request to its stdin and
closes it, then reads one JSON answer from its stdout; logs go to stderr. Protocol version 1,
checked against `protocol.schema.json` ([Connect your app](/docs/connect)).

The request for `late-cancel` under `configs/booking.yaml`:

```json
{"protocol": 1,
 "case": {"id": "late-cancel", "inputs": {"ticket": "/abs/path/golden/booking/late-cancel.txt"}},
 "config": {"model": "gpt-5.4-mini-2026-03-17",
            "prompt": {"system": "/abs/path/prompts/system.md", "summary": "/abs/path/prompts/summary.md"},
            "input": "ticket", "params": {"temperature": 0}}}
```

An answer that passes its six checks:

```json
{"protocol": 1,
 "output": {"reply": "Booking B-1042 is cancelled. The late-cancellation fee applies."},
 "input_tokens": 3275, "output_tokens": 83,
 "model": "gpt-5.4-mini-2026-03-17",
 "trace": {"steps": [
   {"kind": "llm", "actor": "agent", "status": "ok", "model": "gpt-5.4-mini-2026-03-17",
    "tokens_in": 980, "tokens_out": 24, "cost_usd": null},
   {"kind": "tool", "actor": "agent", "status": "ok", "name": "find_booking", "args": {"booking_id": "B-1042"}},
   {"kind": "llm", "actor": "agent", "status": "ok", "model": "gpt-5.4-mini-2026-03-17",
    "tokens_in": 1105, "tokens_out": 21, "cost_usd": null},
   {"kind": "tool", "actor": "agent", "status": "ok", "name": "cancel_booking", "args": {"booking_id": "B-1042"}},
   {"kind": "llm", "actor": "agent", "status": "ok", "model": "gpt-5.4-mini-2026-03-17",
    "tokens_in": 1190, "tokens_out": 38, "cost_usd": null}],
  "final_state": null, "state_change": {"bookings": {"B-1042": "cancelled"}}, "stop": "done"}}
```

### Request (stdin)

All fields are required.

| Field | Type | Meaning |
|---|---|---|
| `protocol` | `1` | the protocol version |
| `case.id` | string | the case's id |
| `case.inputs` | object: name → string | input name → absolute path |
| `config.model` | string | the model of the version under test |
| `config.prompt` | string, or object: name → string | the absolute path, or prompt name → absolute path |
| `config.input` | string | which input the version reads |
| `config.params` | object | the config's `params`; a whole float arrives as an integer |

### Answer (stdout)

Only `output` is required.

| Field | Type | Meaning |
|---|---|---|
| `output` | object or `null` | what the checks score; `null` when there is no answer |
| `raw` | any | the model's text; other values are kept as JSON. Default: `output` as JSON |
| `input_tokens`, `output_tokens` | whole number ≥ 0 | default 0; model steps in the trace are priced instead |
| `model` | string or `null` | the model the provider reported; with neither this nor model steps the run stays unpriced |
| `fingerprint` | string or `null` | the provider's mark of the system that answered, such as OpenAI's `system_fingerprint`: a change between runs can explain drift |
| `finish_reason` | string or `null` | why the model stopped, as the provider says it |
| `request_id` | string or `null` | the provider's id of the call |
| `reasoning_tokens` | whole number ≥ 0 | default 0 |
| `trace` | object or `null` | the run's steps and end state, below |
| `protocol` | `1` | any other value stops the whole run and loses that answer's trace |

### `trace`

All fields are optional.

| Field | Type | Meaning |
|---|---|---|
| `steps` | list of steps | in order, step table below |
| `final_state` | any | the world after the run, for `state` checks |
| `state_change` | any | what the run changed |
| `stop` | string or `null` | why the run ended: `done`, `user_stop`, `max_steps`, `max_turns`, `error`, `aborted`; not checked |

Every step has `kind` and `actor` (`agent`, `user`, `system`, `env`).

| `kind` | Required | Often added |
|---|---|---|
| `llm`, `status: ok` | `model`, `tokens_in`, `tokens_out`, `cost_usd` (`null`: the gate prices it) | `ts`, `latency_ms`, `tokens_cached`, `tokens_reasoning`, `finish_reason`, `text`, `tool_calls` (`[{id, name, args}]`), `request_id`, `purpose` |
| `llm`, `status: error` | `error`, `attempt` (1 for a call's first failed try) | `ts`, `latency_ms` |
| `tool` | `status` (`ok`, `error`, `unknown`), `name`, `args` | `call_id`, `result`, `error`, `ts`, `latency_ms` |
| `message` | nothing | `text` |
| `retrieval` | nothing | `docs` (`[{id, …}]`, read by `doc_found`), `query` |

- Token counts are whole-number literals (`3.0` is not one). The gate numbers the steps, replacing any `seq` or
  `run_attempt`.
- A user simulator's calls go under `actor: user`. Ignore request fields you do not know; a breaking change gets a new
  `protocol` number.

Your program's exit codes:

| Exit | Meaning |
|---|---|
| 0 | the answer is on stdout |
| 75 | try again later (rate limit, upstream timeout): the runner backs off and retries |
| 78, 126, 127 | stop the whole run (no quota, wrong key, program not found) |
| any other | this run fails |

A trace printed before a failed exit is kept. An answer that breaks the schema fails the run. On timeout the gate kills
the program and retries ([details](/docs/connect#exit-codes-and-timeouts)).

## Commands

Run `uv run llm-release-gate COMMAND` in a project that lists the gate as a dependency; `--help` lists the flags.

### pr

Gates a pull or merge request from its git checkout, with the target branch in a second worktree. Per pipeline, equal
version hashes give `unchanged` (unless one of the [changes that run every pipeline](#gate-yaml)); otherwise both
versions run in parallel, with results in `OUT/NAME`. With `--cache`, the base's runs come from earlier jobs when they
are recent ([where from](/docs/how-it-decides#where-the-bases-runs-come-from)).

| Flag | Meaning |
|---|---|
| `--base REV` | the target branch's revision, e.g. `origin/main`; required unless `--list` |
| `--out DIR` | results go to `DIR/NAME`; required unless `--list` |
| `--project DIR` | the project's directory, with `gate.yaml`; default `.` |
| `--pipeline NAME` | gate only this pipeline |
| `--list` | check `gate.yaml` and print its pipelines; runs nothing |
| `--cache DIR` | a directory for earlier jobs' runs: the base's runs of the same version on the same set, at most `base_max_age_days` old, are reused from it and, on GitHub, from other jobs' artifacts |
| `--refresh` | with `--cache` and `--out`, on the target branch itself: reuse its version's recent runs, run what is missing and name them for upload; compares nothing |

```sh
uv run llm-release-gate pr --base origin/main --out gate-out
```

### run

Runs one version over a test set, `k` times per case, appending records to a JSONL file. A rerun pays only for the
missing runs.

| Flag | Meaning |
|---|---|
| `--config FILE` | the version's config; required |
| `--golden DIR` | the test set; required |
| `-k K` | runs per case; default 1 |
| `--out FILE` | the JSONL file to append to; required |
| `--workers N` | runs in parallel; default 4 |
| `--prices FILE` | prices each model step of a trace and stamps `prices_hash` |

```sh
uv run --env-file .env llm-release-gate run --config configs/invoice.yaml --golden golden/invoices -k 3 --out runs/invoice.jsonl
```

### gate

Compares two files of runs case by case with the naive rule. It gives `infra error` for different set hashes, cases on
one side only, different scorer versions (unless `--golden` rescores both) and, for a model name without a date, a
pause over an hour or, when both asked for it, different reported models ([why](/docs/how-it-decides#where-the-bases-runs-come-from)).

| Flag | Meaning |
|---|---|
| `--base FILE` | the base version's runs; this or `--no-base` is required |
| `--no-base` | no base version yet: report the candidate alone and exit 0 |
| `--candidate FILE` | the candidate version's runs; required |
| `--threshold PP` | block when the mean score drops by more than this many points; default 5 |
| `--relative` | read `--threshold` as a percentage of the base mean |
| `--golden DIR` | rescore both versions' saved answers with the current scorer, without calling the model |
| `--prices FILE` | add the cost of the decision |
| `--max-cost-per-run USD` | budget: the candidate's mean cost per run; needs `--prices` |
| `--max-latency S` | budget: seconds for the candidate's latency quantile; blocks only when its whole interval lies above |
| `--latency-quantile Q` | the quantile for `--max-latency`; default 0.95 |
| `--json FILE` | write the verdict as JSON |
| `--markdown FILE` | write the comment |

```sh
uv run llm-release-gate gate --base runs/base.jsonl --candidate runs/candidate.jsonl --golden golden/invoices --markdown comment.md --json verdict.json
```

### golden validate

Checks a test set and prints `N cases, sha256 HASH`.

| Argument | Meaning |
|---|---|
| `DIR` | the test set's directory |
| `--manifest FILE` | also fail unless the ids and the hash match the manifest |

```sh
uv run llm-release-gate golden validate golden/invoices --manifest manifests/invoices.yaml
```

### comment

Posts the Markdown as one comment, edited by later runs. It needs a GitHub Actions `pull_request` job with
`GITHUB_TOKEN` (or `GH_TOKEN`) and `pull-requests: write`, or a GitLab CI merge request pipeline with `GITLAB_TOKEN`
(a project access token, `api` scope); elsewhere it exits 1.

| Argument | Meaning |
|---|---|
| `FILE` | the Markdown from `gate --markdown` or `OUT/NAME/comment.md`; if missing, posts an infra-error comment |
| `--name NAME` | the pipeline's name, for one comment per pipeline |
| `--check` | only check that this job can comment, before paying for runs |
| `--dry-run` | print the comment, post nothing |

```sh
uv run llm-release-gate comment gate-out/invoice/comment.md --name invoice
```

## GitHub Actions

Two actions, pinned to the same release, in a workflow in `.github/workflows/`. The job runs on `pull_request`, needs
`permissions: {contents: read, pull-requests: write, actions: read}` and gets the provider's key from the repository's
secrets as an environment variable. On a push, a manual run or a schedule on the default branch, the action runs that
branch's version for later requests instead (optional; its artifact is `llm-release-gate-base-NAME-ATTEMPT`). On
`pull_request_target` it uploads no runs. GitLab and other CI run `pr` and `comment` themselves, with `--cache` on
a cached directory.

`Ilya-Grigoryev/llm-release-gate/setup@v0.1.0-dev.12` installs Python, uv and the project's locked environment:

| Input | Default | Meaning |
|---|---|---|
| `project-dir` | `.` | the project's directory |
| `gate-ssh-key` | empty | a read-only deploy key of the gate's repository, while it is private |
| `python-version` | `3.12` | for uv to find; the project's own pin wins |
| `uv-version` | `0.11.25` | the uv release |

`Ilya-Grigoryev/llm-release-gate@v0.1.0-dev.12` gates one pipeline per step, with `pr --pipeline NAME`:

| Input | Default | Meaning |
|---|---|---|
| `pipeline` | empty | the pipeline; optional when `gate.yaml` has one |
| `project-dir` | `.` | the project's directory, with `gate.yaml` |
| `github-token` | `${{ github.token }}` | writes the comment (`pull-requests: write`) and finds earlier runs (`actions: read`) |
| `cases` | `true` | upload the test set's text files as a second artifact, for the dashboard |
| `cases-retention-days` | `30` | days GitHub keeps that artifact |
| `runs-retention-days` | `14` | days GitHub keeps each version's runs for later jobs; at least `base_max_age_days` |

## Exit codes

`gate` and `pr` exit with the verdict's code; the job fails on any code but 0. Today the `outcome` in `verdict.json` is
never `inconclusive` or `infra error`.

| Code | Outcome | When |
|---|---|---|
| 0 | `pass` | the mean score did not drop by more than `delta`, and no budget is exceeded |
| 0 | `unchanged` | `pr` only: equal version hashes and none of the [changes that run every pipeline](#gate-yaml); nothing ran |
| 0 | no base version (`outcome: "no base"`) | the target branch has no version of this pipeline: the candidate runs alone and does not block |
| 10 | `quality fail` | the mean score dropped by more than `delta` |
| 11 | `inconclusive` | today only when a request removes or renames a pipeline: each `pr` step that would exit 0 exits 11, and the comments get a note. The naive rule never gives it |
| 12 | `budget fail` | quality passed; a cost or latency limit did not |
| 20 | `infra error` | the runs cannot be compared, a step could not run, or the gate failed |
| 1, 2 | — | a Python crash or a usage error, never read as a verdict |

On a pull request from a fork the action runs nothing and its step exits 1 as `not checked`. With several pipelines,
`pr` exits with the worst outcome, in the order 20, 10, 12, 11, 0; each `verdict.json` keeps its own.

| Command | 0 | 1 | 2 |
|---|---|---|---|
| `run` | every run is done | some runs are not done, the program stopped the run (exit 78, 126, 127), or the config, set or price file is broken | usage error |
| `golden validate` | the set is valid (and matches the manifest) | it is not | usage error |
| `comment` | posted, or with `--check`: can comment | cannot comment | usage error |

## What a request writes

`pr` writes each pipeline's results to `OUT/NAME`. The action uploads them as `release-gate-NAME-ATTEMPT`, except
`cases/` (a second artifact, `release-gate-NAME-ATTEMPT-cases`) and the `prepare` logs. Each version's runs that the job
paid for also go up as `llm-release-gate-runs-NAME-VERSION-SET` (16 characters of each hash), for later jobs.

| File | Contents |
|---|---|
| `comment.md` | the comment |
| `verdict.json` | the verdict, below; missing after an `infra error` |
| `base.jsonl`, `candidate.jsonl` | each version's run records, below; no `base.jsonl` without a base version or when nothing ran |
| `base.native.jsonl`, `candidate.native.jsonl` | the raw provider responses, if the pipeline recorded them |
| `base.log`, `candidate.log`, `gate.log` | the logs of the two runners and of the comparison |
| `.prepare-base.log`, `.prepare-candidate.log` | the logs of `prepare` and `uv sync --locked`, printed to the job log |
| `shared.txt` | the versions whose runs this job paid for, as `base NAME` / `candidate NAME`, by the artifact name above |
| `cases/` | the test set's text files (`.yaml`, `.yml`, `.json`, `.txt`, `.md`, `.csv`), never images, and `inputs-url.txt` if `inputs-url` is set |

`verdict.json`:

| Field | Meaning |
|---|---|
| `outcome`, `exit_code` | the outcome and its code |
| `base_mean`, `candidate_mean` | the mean score over each case's first run, 0 to 1; `null` for a side that did not run |
| `diff_pp`, `limit_pp` | candidate minus base, in points; the largest passing drop |
| `rule` | the rule, in words |
| `cases`, `worse` | the number of cases; those that scored lower, as `[case, base, candidate]`, largest drop first |
| `threshold_pp`, `relative` | the threshold as given |
| `base_config`, `candidate_config`, `set_hash` | the two versions' hashes and the test set's |
| `scorer_version`, `rescored` | the scorer; whether the saved answers were rescored |
| `cost_usd`, `prices_hash` | `{base, candidate}` at the gate's prices, runs paid in this job only, and their hash; `null` without prices |
| `budget` | `outcome` (`within` or `over`), `over`, `unchecked`, `runs`, `retried`, `cost_per_run`, `cost_limit`, `latency_q`, `latency_s`, `latency_ci`, `latency_limit`, `level`; `null` without budgets |
| `models_without_date` | undated model names in the runs |
| `runs_per_case` | `{base, candidate}` |
| `base_reused` | `{runs, days_before_candidate}`: base runs that came from earlier jobs, and how much earlier the oldest ran; `{0, null}` when none |

`unchanged` writes only `outcome`, `exit_code`, the three hashes, and `base_mean`, `candidate_mean` and `diff_pp` as
`null`. `no base` has no `limit_pp`, `rule`, `cases`, `worse`, `threshold_pp`, `relative` or `rescored`; its
`base_mean`, `diff_pp`, `base_config` and (with prices) `cost_usd.base` are `null`, `runs_per_case.base` is `0`, and
it has no `base_reused`.

## The record of a run

One JSON line per run of a case and repetition, record version 6, with `error` set for a run without an answer. A run
the account stopped before it paid for anything is not recorded. A rerun appends the missing runs; the gate reads the
last line without an `error`.

| Field | Meaning |
|---|---|
| `record_version` | the format |
| `config_hash`, `set_hash` | the version and the test set; runs on different sets are never paired |
| `commit` | the project's commit, `+dirty` for uncommitted edits; not compared |
| `case`, `rep`, `run_id`, `timestamp` | the case, the repetition (from 0), the runner's invocation, UTC time |
| `requested_model`, `model` | the config's model and the one the provider reported |
| `prices_hash` | the runner's price table; `null` without one, as in every run `pr` starts |
| `output`, `raw` | the parsed answer and the model's text |
| `input_tokens`, `output_tokens`, `reasoning_tokens` | token counts |
| `latency_s`, `wall_s` | the answering attempt's time; the run's clock time, backoff included |
| `fingerprint`, `finish_reason`, `request_id` | what the provider reported |
| `trace` | below; `null` for a pipeline that records none |
| `usage` | per actor: `llm_calls`, `tokens_in`, `tokens_out`, `cost_usd`; `usage_error` if a step could not be summed |
| `scorer_version`, `hits`, `score`, `score_error` | the scorer; each check's result by id; the case score, 0 to 1; why scoring failed |
| `retries`, `error` | the backoffs used; why there is no answer (`null` if it answered) |
| `reused` | `true` on a base run that came from an earlier job; missing otherwise |

The record's `trace`:

| Field | Meaning |
|---|---|
| `v` | the format |
| `steps` | each with `seq`, `kind`, `actor`, `ts`, `run_attempt` and its kind's fields ([Protocol](#protocol)) |
| `final_state`, `state_change` | as reported |
| `stop` | as reported; the runner sets `error` on a failed run with steps and no `stop` |
| `last_attempt` | the runner's final attempt, whose steps checks read |
| `notes` | unrecorded calls, and why |
| `native` | the file of raw provider responses |

Any step may carry `extra`. A model step stores only its new output: the system prompt and the tools are part of the
version.
