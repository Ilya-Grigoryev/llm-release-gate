# How it works

On every pull request, the gate runs two versions of your LLM application on the same test cases: the version on the
target branch and the version in the request. It scores both and comments whether the mean score dropped by more than
you allow.

## One pull request, start to end

`gate.yaml`, at the root of your project, says what to check. Each entry under `pipelines` is one pipeline, with its
own config, test set (`golden`), verdict and comment.

Take a booking assistant, a made-up agent that books, moves and cancels rooms through tools, and a pull request that
rewrites the cancellation rule in its system prompt.

1. **The job starts.** Before any model call, the gate checks that the request is not from a fork and that `gate.yaml`
   is valid, and comments "⏳ running" with the number of cases; the verdict later replaces that note.
2. **The gate checks out the target branch next to the request.** Both trees get your `prepare` command, if any, and
   their own locked dependencies, so a request that updates an SDK is compared with the old SDK.
3. **Each tree works out its version.** If the two [version](#what-a-version-is) hashes are equal, the pipeline is
   `unchanged` and nothing runs.
4. **Both versions run.** The candidate (the request's version) runs `k` times (or in rounds up to `max_spend_usd`) on each [case](#cases) of the
   request's test set, and the base (the target branch's version) next to it in the same job. With `base_max_age_hours`
   above 0 the gate [reuses](/docs/how-it-decides#where-the-bases-runs-come-from) an earlier job's runs of that
   version on the same set within that many hours instead.
5. **Checks score every run.** The case's [checks](#checks) read the answer and the [trace](/docs/connect#traces) of
   steps that produced it, and give the run a score from 0 to 1.
6. **The gate decides and answers.** It applies [its rules](#the-decision), posts the [verdict](#verdicts)
   as a comment, and the job passes or fails with it. It only advises until you make it a required check. The
   [dashboard](/docs/dashboard) reads the runs from the build artifacts.

## What a version is

A version is three things: its config file, the bytes of the prompt files the config names, and the code of the
repository as git sees it. You do not bump a version number.

Any edit to them gives a new version, even a reordered key in the config, a comma in a prompt or an uncommitted
change. These do not count:

- untracked files, such as run records;
- documentation: `README`, `CHANGELOG`, `CONTRIBUTING`, `LICENSE` (bare or as `.md`, `.rst`, `.txt`, `.adoc`, in any
  case, in any directory) and a `docs/` directory at the root of the repository or project;
- CI: `.github/`, at the same two places;
- `gate.yaml`, and the price files and manifests it names;
- the paths in its `ignore`;
- the test sets `gate.yaml` names (a test set it does not name counts as code);
- the other pipelines' configs and prompts.

A `docs/` directory deeper in the tree is code. A `!` pattern in `ignore` takes documentation, CI or ignored paths back
into the version, but nothing else from this list.

## When nothing runs

A pipeline whose version the request leaves as it is gets `unchanged` and costs nothing. Editing one pipeline's prompt
leaves the others unchanged. Editing only test cases runs nothing either, but the verdict is
[`set changed`](/docs/read-a-verdict#set-changed), and a maintainer merges over the check.

The gate skips a pipeline only when both branches' `gate.yaml` agree on `ignore` and on which files belong to which
pipeline. If a request changes either, every pipeline runs, so it cannot hide new code from its own gate. The same
holds when the target branch has no `gate.yaml` yet, or a broken one.

In `ignore`, a trailing `/` takes a directory, `**` crosses directories, and `!` takes files back:

```yaml
# gate.yaml
pipelines:
  booking:
    config: configs/booking.yaml
    golden: golden/booking
ignore:
  - web/          # the front end never reaches the model
  - "!docs/kb/"   # the assistant reads its knowledge base from docs/kb/
```

## Whose rules apply

The rules come from the target branch's `gate.yaml`: `delta`, `alpha`, `k`, `mean`, `checks`, `levels`, `budgets`, `prices`,
`base_max_age_hours` and `max_spend_usd`. What is tested comes from
the request: the candidate's config, the test set, its manifest and `prepare`. A request therefore cannot loosen its own
gate: a raised `delta` applies after merge. If the target branch has no `gate.yaml`, or a broken one, the request's
rules hold.

Both versions run on the request's test set, so a request could pass by editing the cases that catch it. If it changes
the files of a set the target branch's `gate.yaml` names (the files git tracks under `golden`, or the `manifest`), a
verdict that would exit 0 becomes [`set changed`](/docs/read-a-verdict#set-changed) (exit 13). The comment names the
cases added, removed and edited; a maintainer reviews them and merges over the check. A new pipeline has no set to
compare with.

A request that removes or renames a pipeline fails as [`inconclusive`](/docs/read-a-verdict#inconclusive) (exit 11),
and every other pipeline that would exit 0 exits 11 too. The gate catches mistakes, not a hostile author
([Limits](/docs/limits#it-is-not-a-security-control)).

## Cases

A case is one situation your application must handle: a YAML file with its inputs, the expected values, and how to
score an answer. A directory of cases is a test set. A change that no case touches passes unseen, so
writing cases is most of your work ([Write tests](/docs/write-tests)). Here a customer cancels late; the assistant must look
the booking up first, cancel it, and not waive the fee:

```yaml
# golden/booking/cancel-after-deadline.yaml
id: cancel-after-deadline
version: 1   # the case's own revision, not the application's version
input:
  request: inputs/cancel-after-deadline.txt
expected:
  state_change: {bookings: {B-1042: cancelled}}
scoring:
  method: checks
  aggregate: all
  checks:
    - {id: cancelled, kind: state, key: state_change}   # the booking system changed as expected, and nothing else
    - {id: acted, kind: active}                         # the agent called a tool itself
    - {id: looked-up, kind: order, first: find_booking, then: [cancel_booking]}
    - {id: no-fee-waiver, kind: not_called, tool: waive_fee}
    - {id: steps, kind: max_steps, max: 10}
```

## Checks

A check looks at one thing in a run: answer checks read the output, trace checks read the steps, and a `function`
check calls your own code. None of the built-in checks asks a model for an opinion. `aggregate` turns the results into
the case score: `mean` (the default) or `all`. [Write tests](/docs/write-tests) has examples of each check.

## The decision

The gate decides with a rule on the mean and the rule on checks. The naive rule, the default, takes the first run of
each version and blocks when the candidate's mean score is lower than the base's by more than `delta` points (5 by
default: 0.05 on a score from 0 to 1). The betting rule (`mean: betting`) reads every run: it passes when the runs show
a loss smaller than `delta`, blocks when they show a larger one, and otherwise answers `inconclusive`. The rule on
checks reads every run, up to 10 of each version, and blocks when a check passes significantly less often in the candidate; with one run per
version (`k: 1`, the default) it cannot block. `levels` mark checks as critical, which block even when the others only
report, or minor, which only warn ([How it decides](/docs/how-it-decides)). Budgets on cost and latency can turn a pass
into `budget fail`.

In the author's measurement on a support agent, one unchanged version ran 11 times on the same 10 cases. Its mean score was 0.7, 0.6, 0.6, 0.7, 0.5, 0.6, 0.6, 0.4, 0.7, 0.7 and 0.6: two runs differ by 30
points, six times the default `delta`. [How it decides](/docs/how-it-decides) explains the noise and the
[betting rule](/docs/how-it-decides#the-betting-rule-every-run-three-answers).

## Verdicts

Each pipeline gets one verdict, and CI sees its exit code: `pass`, `unchanged` and `no base version` exit 0,
`quality fail` 10, `inconclusive` 11, `budget fail` 12, `set changed` 13 and `infra error` 20. A request from a fork is `not checked`,
and its job fails. [Read a verdict](/docs/read-a-verdict) says what to do with each.
