# Limits and comparison

The gate asks one question per pull request: on your cases, did the request's version score lower than the target
branch's by more than `delta` points, or go over a budget? This page lists what it does not do and how it differs from
other tools.

## It is not a security control

The gate runs the request's code, workflow file and lock file, with the model provider's key your workflow passes
in. A request can change any of these, so the gate catches mistakes, not an author who wants to get past it. It
does stop a request loosening its own rules:

- `delta`, `k`, `budgets` and `prices` come from the target branch's `gate.yaml`; a new value applies after merge.
- A request that changes `ignore`, or which files belong to which pipeline, runs every pipeline.
- A request that removes or renames a pipeline fails as `inconclusive` (exit 11).

The test set, the candidate's config and `prepare` come from the request. Protect the workflow, `gate.yaml`, the test
sets and the lock file with code owners, turn on "Require review from Code Owners" in the target branch's protection
rule, and make the gate's job a required check:

```text
# .github/CODEOWNERS
/.github/    @your-org/release-owners
/gate.yaml   @your-org/release-owners
/golden/     @your-org/release-owners
/uv.lock     @your-org/release-owners
# /golden/ stands for the test-set directories your gate.yaml names in `golden`
# add any other lock file that `prepare` installs from, such as /package-lock.json
```

## No model grades the text

Every built-in check is code and asks no model for an opinion, so it gives the same result for the same answer every
time. Tone, politeness and helpfulness are checked only if you express them in a `function` check. A
model-graded check you turn on yourself is planned, without a date.

## It cannot see a change no case touches

Say your booking assistant (a made-up example) may refund up to €30 without a manager's approval, and your cases ask for
refunds of €20 and €60: raising the limit to €40 changes nothing any case sees. Changes outside the version stay unseen
too ([What it catches](/docs/what-it-catches#what-it-cannot-see)).

## Today it decides on one run per version

The gate compares each version's mean score over the first run of each case and blocks when the candidate's is lower
by more than `delta` points. In the author's measurement on a support agent, one unchanged version on the same 10 tasks
had a spread of 30 points over 11 runs, and twice the same version, run as base and as candidate in one job, differed by
10 points. So a block or a pass can be noise. Requests within `base_max_age_days` compare with the same base runs, so
one noisy base run moves all their verdicts. A loss smaller than `delta` passes, so small losses add up unseen.
Planned: several runs per version, an interval around the difference, a "not sure yet" outcome, and an anchor version
that only a person moves ([How it decides](/docs/how-it-decides#planned-several-runs-and-an-interval)).

## How it differs from other tools

The gate runs each version from its own checkout. It reuses the target branch's runs for up to `base_max_age_days`
(3 by default; `0` runs both versions in the same job) and refuses to compare runs on different test sets or scored by
different scorers (`infra error`, exit 20).

The table compares only how each tool decides that a new version is worse, as documented in October 2026.

| Tools | What their documentation describes | Compared with this gate |
|---|---|---|
| Evaluation frameworks: promptfoo, Braintrust, Inspect AI, LangSmith | writing and running evaluations with repeated runs; some compare against a baseline | none describes a built-in rule that separates a drop from noise; this gate's rule does not either yet |
| Small statistical gates (2026): statgate, assay-evals, pytest-probability, flipcheck | a statistical test or interval around the difference, paired case by case; some add a margin of loss, a "not sure" outcome or more runs where unclear | they have a statistical rule today, this gate's is planned. Their base is an earlier report, a last passing run or the workflow's choice; this gate runs the target branch's version in the same job |
| ease.ml/ci (Renggli et al., MLSys 2019) | a CI system accepting a new model only when a statistical condition against the old one holds | statistical gates predate LLMs; LLMs add that one version answers differently from run to run |

statgate, assay-evals and flipcheck report checks of their decisions on synthetic or simulated data. This gate has no
such numbers yet and does not claim to decide better ([Method](/docs/method)).
