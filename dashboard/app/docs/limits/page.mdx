# Limits and comparison

The gate asks one question per pull request: on your cases, did the request's version score lower than the target
branch's by more than `delta` points, or go over a budget? This page lists what it does not do and how it differs from
other tools.

## It is not a security control

The gate runs the request's code, workflow file and lock file, with the model provider's key your workflow passes
in. A request can change any of these, so the gate catches mistakes, not an author who wants to get past it. It
does stop a request loosening its own rules:

- `delta`, `alpha`, `k`, `mean`, `checks`, `levels`, `budgets`, `prices`, `base_max_age_hours` and `max_spend_usd` come from the target branch's
  `gate.yaml`; a new value applies after merge.
- A request that changes `ignore`, or which files belong to which pipeline, runs every pipeline.
- A request that removes or renames a pipeline fails as `inconclusive` (exit 11).

The test set, the candidate's config and `prepare` come from the request. Protect the workflow, `gate.yaml`, the test
sets and the lock file with code owners, turn on "Require review from Code Owners" in the target branch's protection
rule, and make the gate's job a required check:

```text
# .github/CODEOWNERS
/.github/    @your-org/release-owners
/gate.yaml   @your-org/release-owners
/golden/     @your-org/release-owners
/uv.lock     @your-org/release-owners
# /golden/ stands for the test-set directories your gate.yaml names in `golden`
# add any other lock file that `prepare` installs from, such as /package-lock.json
```

## No model grades the text

Every built-in check is code and asks no model for an opinion, so it gives the same result for the same answer every
time. Tone, politeness and helpfulness are checked only if you express them in a `function` check. A
model-graded check you turn on yourself is planned, without a date.

## It cannot see a change no case touches

Say your booking assistant (a made-up example) may refund up to €30 without a manager's approval, and your cases ask for
refunds of €20 and €60: raising the limit to €40 changes nothing any case sees. Changes outside the version stay unseen
too ([What it catches](/docs/what-it-catches#what-it-cannot-see)).

## By default it decides on one run per version

The default naive rule compares each version's mean score over the first run of each case and blocks when the
candidate's is lower by more than `delta` points. In the author's measurement on a support agent, one unchanged version on the same 10 tasks
had a spread of 30 points over 11 runs, and twice the same version, run as base and as candidate in one job, differed by
10 points. So a block or a pass can be noise. With `base_max_age_hours` above 0, requests within the age limit compare
with the same base runs, so one noisy base run moves all their verdicts. Runs of one job are also more alike than
independent repeats would be: on 16.11.2026 up to 19 of 30 receipts got the same answer in all 5 runs, and a
different one the day before. The rules count each run as fresh evidence, so their bounds on wrong verdicts are
optimistic until that is measured. A loss smaller than `delta` passes, so small losses add up unseen. The
rule on checks reads every run but cannot block on one run per version: at the default `alpha` a single broken check needs 4 runs of each.

`mean: betting` reads every run and answers `inconclusive` when the runs show neither a pass nor a block. The comment
then says how many runs a pass needs at least. With few cases that number is large, noise adds more, and every run
costs model calls. With `max_spend_usd` the gate buys those runs itself until the limit is spent; a pass still needs round
5 while checks may block, and a set of 10 cases needs about 10 rounds when nothing changed
([Adaptive runs](/docs/how-it-decides#adaptive-runs-a-money-limit-instead-of-k)). Planned: an anchor version that only a
person moves.

## How it differs from other tools

The gate runs each version from its own checkout. It runs both versions in the same job by default and reuses the
target branch's runs only within `base_max_age_hours` and refuses to compare runs on different test sets or scored by
different scorers (`infra error`, exit 20).

The table compares only how each tool decides that a new version is worse, as documented in October 2026.

| Tools | What their documentation describes | Compared with this gate |
|---|---|---|
| Evaluation frameworks: promptfoo, Braintrust, Inspect AI, LangSmith | writing and running evaluations with repeated runs; some compare against a baseline | none describes a built-in rule that separates a drop from noise; this gate's default does not either, `mean: betting` does |
| Small statistical gates (2026): statgate, assay-evals, pytest-probability, flipcheck | a statistical test or interval around the difference, paired case by case; some add a margin of loss, a "not sure" outcome or more runs where unclear | this gate has one too, `mean: betting`, but not as its default. Their base is an earlier report, a last passing run or the workflow's choice; this gate runs the target branch's version itself, or reuses its runs from the last few days |
| ease.ml/ci (Renggli et al., MLSys 2019) | a CI system accepting a new model only when a statistical condition against the old one holds | statistical gates predate LLMs; LLMs add that one version answers differently from run to run |

statgate, assay-evals and flipcheck report checks of their decisions on synthetic or simulated data. This gate has no
such numbers yet and does not claim to decide better ([Method](/docs/method)).
