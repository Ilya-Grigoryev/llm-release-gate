# Write tests

The gate notices a change only where one of your cases looks. [Reference](/docs/reference#terms) defines the terms.

## Four questions for every case

A case is one situation your app must handle: its inputs, what you expect, and the checks that compare a run with that
expectation. Answer four questions:

1. **The result**: what must the answer say? ([Answer checks](#answer-checks))
2. **The actions**: what must the app do, in which order, and never do? ([Trace checks](#trace-checks))
3. **The state of the world**: what must have changed, and what not? (`state`)
4. **The limits**: how many steps, which calls are off limits? (`max_steps`, `not_called`)

Anything else that code can express goes in a [`function` check](#your-own-check). Cost and latency are budgets for the whole version in
`gate.yaml`, not per-case checks.

## The case file

Each case is one YAML file at the top of the test set's directory ([fields](/docs/reference#fields-of-a-case)). Put
input files in a subdirectory such as `inputs/`, since every YAML file at the top level is read as a case, and quote
dates.

A made-up booking assistant: a customer cancels a booking that cost €80 and asks for the money back. Refunds above €50
need a person, so the assistant looks the customer up, cancels and hands the refund to staff:

```yaml
# golden/booking/refund-over-limit.yaml
id: refund-over-limit
version: 1
slices: {topic: refunds}
input:
  request: inputs/refund-over-limit.txt   # the customer's message
  world: inputs/world.yaml                # bookings and customers before the run
expected:
  state_change: {bookings: {B-2207: cancelled}}
  actions:
    - {tool: cancel_booking, args: {booking_id: B-2207}}
    - {tool: hand_to_staff}
scoring:
  method: checks
  aggregate: all
  checks:
    - {id: state, kind: state, key: state_change}   # this change and no other
    - {id: acted, kind: active}                     # the agent made a tool call that did not fail
    - {id: looked-up, kind: order, first: find_customer, then: [cancel_booking, move_booking, refund]}
    - {id: did, kind: actions, expected: actions}   # one result per expected action
    - {id: no-big-refund, kind: not_called, tool: refund, args: {amount_eur: {gt: 50}}}
    - {id: steps, kind: max_steps, max: 12}
```

`state` compares the whole `state_change` your program reports, so an extra change, such as a refund, fails it. A run
that cancels the booking and pays the €80 itself fails `state`, `did.1:hand_to_staff` and `no-big-refund`.

An invoice reader uses `method: field_match` ([Get started](/docs/start#5-write-a-first-case)): a field expected as
`null` is not scored, and `type: date` or `type: number` compare by value. Dates with slashes or dots are read day first
unless that is impossible. Amounts in `€` or with a decimal comma do not parse as numbers.

## Answer checks

A check gives true, false, a share between 0 and 1, or nothing when it does not apply. Answer checks read the output, or
the part at the path in `field`. `exact`, `contains`, `number` and `refusal` compare with their own `value`, or with the
case's expected value at the path in `expected`.

| Kind | Passes when |
|---|---|
| `field_match` | each field in `expected.fields` matches; one result per field |
| `exact` | the text equals the value, ignoring spaces around it |
| `contains` | the text contains the value, ignoring case |
| `regex` | `pattern` matches somewhere in the text |
| `number` | the number is within `tol` of the value |
| `json_schema` | the value is valid against the JSON Schema in `schema` |
| `refusal` | with `value: true`, the field (default `answer`) is present and `null`; with `false`, filled |

## Trace checks

Trace checks fail on a run without a trace and read the agent's steps unless `actor` is `user`, `system` or `env`.

| Kind | Passes when |
|---|---|
| `called` | `tool` was called with matching `args`, and the call did not fail |
| `not_called` | `tool` was never tried with such `args`; a refused call counts as tried |
| `order` | every call of a `then` tool comes after a call of `first` |
| `max_steps` | at most `max` answered model calls |
| `active` | at least one tool call did not fail |
| `actions` | per expected action: a matching call that did not fail |
| `state` | `final_state` (default) or `state_change`, per `key`, equals the expected one |
| `doc_found` | a share: the expected document ids that were retrieved |

In `args`, a plain value must match exactly and a mapping holds operators ([Reference](/docs/reference#checks)). Wrap
your tools so the trace knows which calls failed ([Connect your app](/docs/connect)).

## Your own check

A `function` check calls your Python function, named `module:function`, with the expected values, the output, the trace
and the check's entry, and returns true, false, a share or `None`.

```python
# booking_assistant/checks.py
import re


def names_the_booking(expected, output, trace, check):
    """The reply names the case's booking and no other booking."""
    reply = (output or {}).get("reply")
    if not isinstance(reply, str):
        return False
    return set(re.findall(r"B-\d+", reply)) == {check["booking"]}
```

```yaml
    - {id: names-booking, kind: function, function: "booking_assistant.checks:names_the_booking", booking: B-2207}
```

`booking` is a key of your own. Put the module in your project's package: `golden validate` imports it, and editing it
makes a new version. No built-in check asks a model for an opinion. Checks shared by a whole set are planned
([The list grows](/docs/what-it-catches#the-list-grows)).

## From checks to a case score

`aggregate: mean` (the default) averages the results, leaving out results that do not apply. `all` gives 1 only if every
result that applies is a full pass: use it when the checks describe one correct outcome, such as an agent's task.

With `all`, each case is worth 100 / N points: with 20 cases, one case that goes from 1 to 0 lowers the mean by exactly
5 points, which the naive rule (block above `delta`, 5 by default) passes; the rule on checks blocks it from 4 runs
of each version if one check broke, later if several did.

`levels` in `gate.yaml` names checks by id: a minor check leaves the case score and only warns when it gets worse, a
critical one blocks even under `checks: report`
([Critical and minor checks](/docs/how-it-decides#critical-and-minor-checks)). Give checks ids that say what they
check, so one pattern can name a kind of check across cases.

## Cover the edges

A rule decides at its edges, so put cases there:

- **Both sides of every limit.** If refunds above €50 need a person, write cases at €40, at exactly €50 and at €60.
  With cases only at €40 and €80, raising the limit to €70 changes nothing they see.
- **Missing, wrong and ambiguous data**: an invoice without a VAT id, a customer with two bookings who says "cancel my
  booking".
- **Requests to refuse**, **formats** and **paraphrases**, as separate cases.

An expected `null` means "not scored". To require an empty field, add a check such as
`{id: no-vat-id, kind: json_schema, field: vat_id, schema: {type: "null"}}`.

## Make sure doing nothing fails

`not_called`, `order`, `max_steps` and `state` expecting no change all pass on a run with no tool calls, so an agent
that stops acting looks better than it is. The trap is worst where the right answer is to change nothing:

```yaml
# golden/booking/cancel-for-other-customer.yaml
id: cancel-for-other-customer
version: 1
input:
  request: inputs/cancel-for-other-customer.txt
  world: inputs/world.yaml
expected:
  state_change: {}          # nothing may change; write "no change" the way your program reports it
scoring:
  method: checks
  aggregate: all
  checks:
    - {id: state, kind: state, key: state_change}
    - {id: no-cancel, kind: not_called, tool: cancel_booking}
    - {id: acted, kind: active}   # without it, an agent that does nothing passes this case
```

Without `acted`, an agent that answers "Sorry" and calls no tool scores 1 here. Pair `not_called` with `active` or a
`called` check in every agent case, use `aggregate: all`, and try a version whose prompt tells the agent to apologise
and stop.

## Try new cases on the current version

Run the current version on a new case a few times:

```sh
uv run --env-file .env llm-release-gate run --config configs/booking.yaml --golden golden/booking -k 3 --out runs/try.jsonl
jq -r '[.case, .rep, .score] | @tsv' runs/try.jsonl
```

A case should pass on a version you consider correct. If it passes on some runs and fails on others, find out why: a
check that demands exact wording of free text fails at random. In the author's measurement on a support agent, one
unchanged version scored a mean of 0.7, 0.6, 0.6, 0.7, 0.5, 0.6, 0.6, 0.4, 0.7, 0.7 and 0.6 over 11 runs of the same 10
tasks, and by default (`k: 1`) the gate decides on one run per version ([How it decides](/docs/how-it-decides)).

A prompt tuned until the CI cases pass can end up fitted to them. Keep some cases in a directory that `gate.yaml` does
not name, list it in `ignore`, and run them rarely.

## Change cases with the behaviour

When a request changes behaviour on purpose, such as a new refund limit, update the old cases in the same request: both
versions are scored against the request's cases. A request that changes only cases runs nothing, so [run new cases
yourself](#try-new-cases-on-the-current-version).

## Validate the set

```sh
uv run llm-release-gate golden validate golden/booking
```

Without running anything, it checks each case, its inputs and its checks, and prints the set's hash. A set kept outside
git, such as scans with personal data, is pinned by a [manifest](/docs/reference#manifest).
