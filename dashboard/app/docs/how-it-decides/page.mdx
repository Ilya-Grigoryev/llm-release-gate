# How it decides

The gate runs two [versions](/docs/how-it-works#what-a-version-is) of your application on the same
[cases](/docs/how-it-works#cases): the base, from your target branch, and the candidate, from the pull request. Your
[checks](/docs/how-it-works#checks) score each run.

## The same version answers differently

The same version, run twice on the same cases, can get two different scores: the model does not always give the same
answer, even at temperature 0 with a dated model snapshot. The figure shows the author's measurement: 11 runs of a
support agent with nothing in it changed.

The range is 0.40 to 0.70, 30 points. Two cases passed in every run; the other eight passed in some runs and failed in others."} />

The mean ranged from 0.40 to 0.70: 30 points, six times the default `delta` of 5 points. A twelfth run of the same
version, on 29 October, scored 0.80. Files outside the agent changed between some of the first eight runs, but even the
last three, from one `run` call in one checkout, disagreed on 4 of the 10 cases. Noise depends on the application: in
the author's runs, a one-call extraction pipeline on 30 documents moved by less than 2 points over 10 runs.

## Why one run is not enough

A pull request to the same agent that only fixed typos in its instructions scored 0.60 against 0.70 for the base, and
the naive rule blocked it. One run of each version cannot tell whether that loss is real: the unchanged agent moved
between 0.40 and 0.70 by itself.

<Fig id="how-it-decides-2" caption={"A pull request that only fixed typos scored 10 points lower and was blocked. The unchanged agent alone covered 30 points, so one run of each version cannot say whether the drop is real."} alt={"The base scored 0.70 and the typo fix 0.60, a drop of 10 points; the naive rule blocks drops of more than 5 points, so it blocked. Both scores lie inside the range 0.40 to 0.70 that the same agent covered on its own, with nothing in it changed."} />

Equally, a base run that lands low can let a worse candidate pass. The [betting rule](#the-betting-rule-every-run-three-answers)
reads every run instead.

## The default: the naive rule and the rule on checks

On every pull request that changes the version, the gate:

1. has both versions' runs on the request's test set, `k` per case (default 1), the base's from an earlier job when
   they are recent; the naive rule reads the first run of each case, the rule on checks every run;
2. returns `infra error` (exit 20) unless both sides have the same set hash, the same scorer and a result for every
   case;
3. takes each version's mean score and computes the difference in points: 100 × (candidate mean − base mean);
4. blocks with `quality fail` (exit 10) when the difference is below −`delta`, 5 points by default;
5. blocks with `quality fail` too when a check passed significantly less often in the candidate's runs than in the
   base's (Fisher's exact test per case and check, one-sided, at half of [`alpha`](#how-often-the-gate-may-be-wrong),
   0.025 by default, corrected for the number of checks that could show it). With one run of each version this cannot
   happen: at the default `alpha` a single broken check can block from 4 runs of each, several broken at once need more. `checks: report` only lists it, and [levels](#critical-and-minor-checks) set
   which checks may block;
6. checks the [budgets](#budgets-cost-and-latency), if you set any.

```yaml
pipelines:
  support:
    config: configs/support.yaml   # the version
    golden: golden/support         # its test set
k: 1        # runs per case and version; the mean uses the first, checks all
delta: 5    # block when the mean score drops by more than 5 points
```

The rules come from the target branch's `gate.yaml`, so raising `delta` in a pull request does not loosen its own gate
([Whose rules apply](/docs/how-it-works#whose-rules-apply)). Outside CI, the `gate` command
([Reference](/docs/reference)) gives the same verdict from two files of runs.

## The betting rule: every run, three answers

With `mean: betting` the gate reads every run of both versions, and `delta` (δ in the figures) becomes the loss you
accept, set before you see any results. The rule answers one of three things:

- **pass**: the runs show that the candidate loses less than `delta`. When they also show it is worse than the base,
  the comment warns.
- **block** (`quality fail`, exit 10): the runs show that it loses more than `delta`.
- **inconclusive** (exit 11): the runs show neither. The comment says how many runs of each version a pass needs and
  roughly what the missing runs cost.

```yaml
k: 5            # runs per case and version, at least 2; the betting rule reads them all
delta: 5        # the loss you accept, in points
mean: betting   # the default is naive
```

The rule pairs run 1 of a case in the candidate with run 1 of the same case in the base, run 2 with run 2, and so on,
so a hard case is hard on both sides. It takes its first look after 2 runs of each version, so with `k: 1` it can only
answer `inconclusive`. Then it looks again after every run, and the first look that shows a side decides.

However many looks the rule takes over the same runs, the chance of a wrong pass, where the candidate in truth loses
more than `delta` on these cases, stays at most the rule's share of `alpha`; the same holds for a wrong block. At the
default `alpha` the share is 2.5 %, or 5 % when no check can block
([How often the gate may be wrong](#how-often-the-gate-may-be-wrong)). The promise needs runs
that go wrong independently of each other, and base runs reused from an earlier job that still behave like today's. When
a whole run goes bad at once, say the provider changes something for an hour, the errors grow, and the gate cannot tell.
The comment gives the run that decided and a range for the difference at that run
([Read a verdict](/docs/read-a-verdict#lines-of-the-betting-rule)). The range covers 1 − 2 × the rule's share: 95 % at
0.025.

The method is a betting confidence sequence (Waudby-Smith and Ramdas,
[arXiv:2010.09686](https://arxiv.org/abs/2010.09686)). For each side the gate bets on the paired differences, run after
run, and the side whose stake grows 1 / α-fold decides, where α is the rule's share: 40-fold at 0.025. The bet stays fixed within a run, which keeps the
guarantee when cases differ in difficulty.

The runs a pass needs depend on the number of cases and on `delta`, and few cases need many. The comment states the
number for your set: what a candidate that scores like the base in every run would need. Noise adds more. Outside CI,
a second `run` with a larger `-k` appends only the missing runs, and `gate` decides again over all of them: that keeps
the bound. A new CI job is different: it runs the candidate again from the start, so it is a new test, and running jobs
until one passes makes a wrong pass more likely than the bound. To use more runs in CI, raise `k` in the target branch's
`gate.yaml`, in a request of its own, before the job. Continuing a request with the runs it already paid for is planned
([Reference](/docs/reference#gate)).

Planned: when the answer is `inconclusive`, the gate buys the missing runs itself, up to a money limit you set, and
continues in the same request. Also planned: a second comparison against an anchor, a fixed earlier version that only a
person moves, so that small losses cannot pile up. Until experiments measure the rules on recorded runs, this site
states no measured error rates.

## How often the gate may be wrong

Each of the two rules can block on its own, so the gate's chance of blocking a candidate that is no worse adds up over
both. Under `mean: betting`, `alpha` in `gate.yaml` bounds that sum, 0.05 by default, and the gate splits it:

```yaml
alpha: 0.05   # the whole gate: 0.025 to the rule on the mean, 0.025 to the rule on checks
```

- With `mean: betting` and checks that may block, each rule gets half.
- If no check can block (`checks: report` without `critical` levels), the rule on the mean gets all of it.
- The betting rule's share bounds both of its errors: a wrong block, and a wrong pass of a candidate that lost more
  than `delta`. Raising `alpha` to decide sooner lets more such losses pass.
- The naive rule has no bound; under `mean: naive` the rule on checks gets its half and the rest goes unused.

The comment says how the gate spent its `alpha`, for example "False blocks: at most α 0.05 for the gate, 0.025 for the
rule on the mean and 0.025 for the rule on checks." A lower `alpha` needs more runs before the gate decides. At
`delta` 5:

| `alpha` | Each rule's share: false blocks, and missed losses for the betting rule | A check broken in every run can block from | Fully broken checks that can still block at `k: 5` | Runs of each version a pass needs when nothing changed, 10 / 30 / 50 cases |
|---|---|---|---|---|
| 0.01 | 0.005 | `k: 5` | 1 | 14 / 5 / 3 |
| 0.025 | 0.0125 | `k: 5` | 3 | 12 / 4 / 3 |
| 0.05 (default) | 0.025 | `k: 4` | 6 | 10 / 4 / 2 |
| 0.1 | 0.05 | `k: 3` | 12 | 8 / 3 / 2 |

The table assumes checks that may block. With none, the rule on the mean gets all of `alpha`: its runs are in the row
whose share equals your `alpha`, the 0.1 row at the default. The fourth column is a limit of Tarone's correction: when more checks than that break in every run, it blocks none of
them, and the rule on the mean has to catch the break. If the pipeline's `k` is too small for any check to block at its
`alpha`, `pr` says so in the job's log before the runs start and names the `k` or `alpha` that would let one block. Like `delta`, `alpha` comes from the target branch's `gate.yaml`.

## Critical and minor checks

By default every check counts the same. `levels` in `gate.yaml` marks some checks as critical and some as minor; the
rest stay normal:

```yaml
levels:
  critical: ["no-*", cancelled]   # block even under checks: report
  minor: [steps]                  # out of the case score; only warns
  cases:
    "smalltalk-*": minor          # every check of these cases
```

- **critical**: a check that passes significantly less often blocks under `checks: block` and `checks: report` alike,
  and the comment opens with it: "❌ Critical checks broke: `no-fee-waiver` in cancel-after-deadline."
- **minor**: the check leaves the case score, so it never moves the mean and never blocks. When it passes significantly
  less often, the comment's title gets "⚠️ 1 minor check worse", the JSON verdict a `warnings` entry and GitHub Actions
  a warning on the job; the exit code stays. Once `levels` is set, a normal check under `checks: report` warns the same
  way, and the title then says "reported check".
- **cases**: a pattern of case ids gives a level to that case's checks that have none of their own. A case set to
  `minor` makes all its checks minor, critical ones included, and a case with only minor checks leaves the mean.

Patterns are shell-style: `no-*` matches every check id that starts with `no-`. The comment names a pattern that
matches no check of the set, so a typo cannot leave checks normal unnoticed. Where ids are positions, a pattern names a
position: in the author's telecom-support app, `assert-N` is the N-th assertion of each task, so `assert-1` is a
different rule in each case.

The rule on checks tests two families apart, each at half of `alpha` (0.025 by default) with its own correction: the
checks that may block (critical ones, and normal ones under `checks: block`) and the checks that only report (minor
ones, and normal ones under `checks: report`). The second family never blocks, so it spends none of the gate's bound.
Without `levels` nothing changes.

## Where the base's runs come from

A version stays the same version in any commit ([What a version is](/docs/how-it-works#what-a-version-is)), so the gate
runs it once and shares the runs. Each job uploads the runs it paid for as an artifact named after the version and the
test set. Before running the base, the next job looks for that artifact and reuses its runs when they are at most
`base_max_age_days` old, 7 by default. A merged request's candidate is the target branch's new version, so the next
request usually finds its base already run. The comment says how many base runs came from earlier jobs, and its cost
counts only the runs this job paid for.

Reuse has two prices:

- **Drift.** A model's behaviour under one name can shift. In the author's runs with a dated snapshot, the server
  configuration the provider reported changed between repeats of the same request, and the level of noise differed
  between two days. Within the age limit, such a shift counts as an effect of your change. With
  `base_max_age_days: 0` both versions run together, and a shift that hits both cancels out.
- **Shared luck.** Every request within the age limit compares with the same base runs. With one run per case, a lucky
  or unlucky base run moves all their verdicts the same way. Use `0` when you count the gate's errors across requests.

The gate never reuses runs when the request changes `prepare` or when the target branch has no valid `gate.yaml`. It
takes one model name for one model, with or without a date: Anthropic's ids from Claude 4.6 on are fixed snapshots, while
other providers' names without a date may move to a newer snapshot. Prefer a dated snapshot there. For a model without a
date the comment warns, and the gate refuses to compare (`infra error`) runs the provider reported as different models
when both versions asked for the same one. If the provider moves the name to another model, requests get that error until
the target branch's cached runs are older than `base_max_age_days`; set it to `0` on the target branch until then.
Reuse needs `actions: read` in the job's `permissions`; without it the base runs again and the comment says why.

## Budgets: cost and latency

Both work today and are set in `gate.yaml`:

```yaml
pipelines:
  support:
    config: configs/support.yaml
    golden: golden/support
prices: prices.yaml          # list prices; commit this file
budgets:
  cost_per_run_usd: 0.02     # the candidate's mean cost per run, at these prices
  latency_s: 20              # limit in seconds for the latency quantile
  latency_quantile: 0.95     # the default
```

```yaml
# prices.yaml: USD per 1M tokens, [input, output] or [input, output, cached input]
# example prices; use your provider's current list prices
gpt-5.4-mini-2026-03-17: [0.75, 4.50, 0.075]
```

**Cost.** The gate prices every model call of each candidate run and blocks when the mean cost per run is above
`cost_per_run_usd`. With a cost budget, a missing `prices` or a model missing from the price file gives `infra error`.

**Latency.** The gate blocks only when a 95 % interval around the quantile of the candidate's run latencies (0.95 by
default) lies wholly above the limit: with 10 runs, at least three must be over it. A run with no answer is an error,
not a latency, and with `k` above 1 the interval is narrower than it should be.

A budget only turns a quality pass into `budget fail` (exit 12).

## What a pass means

A pass means, on your cases and under the target branch's rules: the rule on the mean passed, no check that may block
got significantly worse over the runs, and the candidate was not shown over any budget you set. Under the naive rule,
the candidate's first run had a mean score no more than `delta` points below the base's; under the betting rule, the
runs showed a loss smaller than `delta`. It does not mean:

- **The change is safe on new inputs.** The gate answers only for your cases.
- **Nothing got worse.** Losses smaller than `delta` pass and can add up, a minor check only warns, and a mean that
  holds can hide one check that got worse when there are too few runs to show it.
- **Every change was tested.** Say your booking assistant (a made-up example) may refund up to €30 without approval,
  and your cases ask for €20 and €60. Raise the limit to €40, and no case can tell the two versions apart.
- **The author meant well.** The gate catches mistakes, not a hostile author.

[Read a verdict](/docs/read-a-verdict) covers outcomes that pass without comparing anything, and those that do not pass.
